# Misja AED Prototype Implementation Plan

> **For agentic workers:** Implement inline in this workspace. Use test-driven development for domain, import, and export behavior.

**Goal:** Build a working, offline-capable contest prototype that collects, normalizes, verifies, moderates, and prepares AED data for publication, with an accessible public lookup view and the required contest artifacts.

**Architecture:** Use a modular TypeScript application. Keep the AED domain, source adapters, validation, duplicate review, and export package independent of the web framework; expose them through a small application API and present public, contributor, and moderator workflows in the web UI. Use a local demo data store for a no-service demo while keeping a repository boundary for a later PostgreSQL deployment.

**Tech Stack:** TypeScript, Next.js/React, Node.js LTS, Zod runtime validation, a local persistent prototype store, Vitest, Playwright, and axe-core where the environment supports them. Use Leaflet with a non-blocking accessible list fallback; no paid map API.

**Spec:** User-provided contest PDF and the 18-page `Dokument bez nazwy.pdf` prompt, both reviewed in this conversation.

## Global Constraints

- The public API documentation currently located lists read endpoints; do not claim the app publishes directly to dane.gov.pl.
- The app must distinguish source facts, reported status, access schedule, verification event, and unknown values.
- Preserve source record identifiers, upstream origin, timestamps, license, attribution, and raw input through normalization.
- Deduplication only suggests candidates; a human decides whether to merge, and multiple AEDs in one building remain possible.
- Synthetic demo records must be clearly labelled and separated from imported records.
- Exports must be machine-readable; provide CSV, JSON, GeoJSON, and the required XLSX schema workbook.
- Provide a map and an equivalent list; the list must work when map tiles or network access are unavailable.
- Do not include personal contact details in public exports. Keep demo administration clearly non-production.
- Do not claim WCAG conformance from automated checks alone; run keyboard and screen-reader-oriented checks where practical.
- Produce the contest materials: project description, user steps, limitations, code, logo formats, brandbook, and a presentation with actual application screenshots.

## Review Focus

- Malformed CSV/GeoJSON/XLSX, Polish characters, BOM, separators, and oversized inputs must produce actionable validation errors rather than crash the app.
- Incorrect or swapped coordinates must be flagged without silently changing them; GeoJSON order stays longitude then latitude.
- Missing access/status values remain `unknown`; `24/7` and recent import never imply operational verification.
- Nearby records and records with shared OSM provenance remain candidates, not automatic independent confirmations or merges.
- Unresolved licensing, unsafe spreadsheet formulas, and private reporter data must be excluded from public export.
